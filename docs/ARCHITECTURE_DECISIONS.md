# تصمیم‌های معماری و داده

## ADR-001: معماری لایه‌ای

جریان وابستگی ثابت است:

`ViewModel → Use Case → Repository Interface → Repository Implementation → DAO`

Repository Interface در Domain Layer و پیاده‌سازی آن در Data Layer قرار می‌گیرد. ViewModel به DAO یا AppDatabase وصل نمی‌شود.

## ADR-002: پایگاه داده Room

AppDatabase باید Singleton و ترجیحاً توسط Hilt فراهم شود. ایجاد مسیر موازی مانند Singleton دستی در کنار Hilt مجاز نیست. Migrationها باید صریح باشند و `fallbackToDestructiveMigration` استفاده نشود.

## ADR-003: نمایش پول

مقدار مالی فقط `Long` و برحسب ریال است. استفاده از `Float` یا `Double` برای مبلغ، مانده، بودجه و بدهی ممنوع است.

## ADR-004: زمان

زمان در دیتابیس Epoch Milliseconds است. تبدیل جلالی و قالب‌بندی فارسی به لایه نمایش تعلق دارد و از دیتابیس مستقل است.

## ADR-005: انتقال داخلی

انتقال داخلی دو سمت مرتبط دارد، دارای `linkedTransferId` و حساب مبدأ/مقصد است. این عملیات مانده حساب‌ها را تغییر می‌دهد اما در درآمد، هزینه و بودجه محاسبه نمی‌شود.

## ADR-006: تراکنش قطعی

Queryهای درآمد و هزینه فقط تراکنش تأییدشده با جهت صحیح را محاسبه می‌کنند. وضعیت‌های `PENDING`، `IGNORED`، `DUPLICATE`، `FAILED`، `PARSE_FAILED` و `REVERSED` در مجموع قطعی وارد نمی‌شوند.

## ADR-007: جلوگیری از تکرار

Fingerprint تراکنش برای تشخیص تکرار استفاده می‌شود و باید Index/محدودیت مناسب و تست هم‌زمانی/تکرار داشته باشد.

## ADR-008: حذف امن

حذف حساب یا دسته نباید سوابق مالی را ناخواسته حذف کند. رفتار Foreign Key باید صریح، آزموده و مستند باشد؛ تراکنش قدیمی حفظ شود.

## ADR-009: امنیت داده بانکی

شماره کامل کارت و حساب، رمزها، CVV2 و اطلاعات ورود ذخیره نمی‌شوند. متن پیامک داده حساس است و در لاگ Release چاپ نمی‌شود.

## ADR-010: عملیات کم‌مصرف با هوش مصنوعی

توسعه به گام‌های کوچک تقسیم می‌شود. ممیزی و Build کامل در پایان فاز انجام می‌شود، نه بعد از هر تغییر جزئی.
