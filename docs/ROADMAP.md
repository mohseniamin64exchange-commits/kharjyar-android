# نقشه راه خرج‌یار

## انجام‌شده طبق گزارش

- فاز ۱: پایه و معماری
- فاز ۲: دیتابیس، Domain/Data، Repository/Use Case و تست پایه

## فاز ۳: دریافت اعلان

برای کاهش مصرف مدل به سه بخش تقسیم شود:

1. NotificationListenerService و مدیریت دسترسی
2. دریافت و فیلتر اعلان‌های برنامه پیامک
3. ذخیره اعلان بانکی به‌عنوان تراکنش در انتظار

خروجی فاز: دریافت امن اعلان بدون Parser کامل، بدون چاپ متن حساس در Logcat و با تست‌های سرویس/فیلتر.

## فاز ۴: Parser پیامک و اعلان بانکی

- استخراج بانک، مبلغ، جهت، تاریخ/ساعت و چهار رقم آخر کارت
- PersianNumberNormalizer مستقل از دیتابیس
- الگوهای قابل توسعه برای بانک‌ها
- تشخیص Fingerprint و تکراری
- ثبت خطای Parse بدون ورود به گزارش مالی

## فاز ۵: جریان تأیید تراکنش

- نمایش Pending Transaction
- اصلاح مبلغ/حساب/دسته
- تأیید، رد، نادیده‌گرفتن و تشخیص تکراری
- ثبت دستی و انتقال داخلی

## فاز ۶: داشبورد و گزارش‌ها

- جمع درآمد، هزینه و مانده
- فیلتر بازه زمانی/حساب/دسته
- نمودارها و جست‌وجو
- حذف انتقال داخلی و وضعیت‌های غیرقطعی از گزارش

## فاز ۷: بودجه، تراکنش تکرارشونده و بدهی

- بودجه دسته‌ای و هشدار مصرف
- Recurring Transaction
- Debt و DebtPayment
- Tag و گزارش مرتبط

## فاز ۸: امنیت و پشتیبان‌گیری

- بررسی رمزنگاری داده‌های حساس مجاز
- قفل برنامه/بیومتریک در صورت نیاز
- Export/Import و Backup امن
- کنترل لاگ Release و سیاست حریم خصوصی

## فاز ۹: تثبیت و انتشار

- تست روی گوشی واقعی و نسخه‌های مختلف اندروید
- Accessibility و RTL
- Performance و مصرف باتری
- امضای Release، ساخت APK/AAB و مستند انتشار

## مسیر احتمالی پرداخت بله (آینده، خارج از هسته فعلی)

در بررسی قبلی مشخص شد بله API رسمی پرداخت برای بازوها دارد و مسیر پیشنهادی می‌تواند چنین باشد: فاکتور خرج‌یار → لینک/فاکتور بله → پرداخت مشتری → تأیید API → ثبت و تطبیق واریزی با payload. اجزای مطرح‌شده شامل Bot Token، provider_token، `sendInvoice`، `createInvoiceLink`، `pre_checkout_query`، `successful_payment` و `inquireTransaction` بوده‌اند. ادعای «بدون اینماد یا مالیات» تأیید نشده و نباید مبنای محصول باشد. پیش از اجرا باید مستندات رسمی و شرایط تجاری روز دوباره بررسی شوند.
