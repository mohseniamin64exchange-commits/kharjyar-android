# راهنمای تحویل پروژه خرج‌یار به هوش مصنوعی

این سند نقطه شروع اجباری برای هر هوش مصنوعی یا توسعه‌دهنده جدید است.

## هدف محصول

خرج‌یار یک اپلیکیشن اندرویدی فارسی برای ثبت و مدیریت امور مالی شخصی است. هسته برنامه باید حساب‌ها، تراکنش‌ها، دسته‌ها، بودجه، بدهی، برچسب‌ها و انتقال داخلی را مدیریت کند. در فازهای بعد، اعلان‌های بانکی دریافت و پس از استخراج اطلاعات، به‌عنوان تراکنش در انتظار ثبت می‌شوند تا کاربر آن‌ها را تأیید یا اصلاح کند.

## وضعیت تحویل

دو فاز نخست در Google AI Studio پیاده‌سازی و طبق گزارش همان محیط Build و تست شده‌اند. سورس در زمان نگارش این سند هنوز به این مخزن منتقل نشده است. بنابراین ادعاهای زیر «گزارش وضعیت قبلی» هستند و باید بعد از ورود سورس با کد واقعی راستی‌آزمایی شوند.

## کارهای گزارش‌شده به‌عنوان انجام‌شده

- معماری لایه‌ای و جداسازی ViewModel از DAO
- پایگاه داده Room و Entityهای فاز دوم
- Repository Interface در Domain و Implementation در Data
- Use Caseهای ضروری حساب، دسته و تراکنش
- دسته‌های پیش‌فرض فارسی با درج idempotent
- Unit Test و Robolectric برای بخش‌هایی از Room و منطق مالی
- Build موفق و اجرای موفق `:app:testDebugUnitTest`

## جریان معماری مورد انتظار

`ViewModel → Use Case → Repository Interface → Repository Implementation → DAO`

ViewModel نباید مستقیماً به DAO یا AppDatabase متصل شود. AppDatabase باید Singleton باشد و ترجیحاً از طریق Hilt تأمین شود.

## قواعد قطعی داده

- تمام مبلغ‌ها `Long` و برحسب ریال ذخیره شوند.
- تاریخ و ساعت اصلی به Epoch Milliseconds ذخیره شود.
- تاریخ شمسی فقط در لایه نمایش محاسبه شود.
- شماره کامل کارت/حساب، رمز، رمز پویا، CVV2 یا اطلاعات ورود بانکی ذخیره نشوند.
- فقط چهار رقم آخر کارت در صورت نیاز مجاز است.
- انتقال داخلی باید `linkedTransferId` و حساب مبدأ/مقصد داشته باشد.
- انتقال داخلی موجودی حساب‌ها را تغییر می‌دهد اما درآمد یا هزینه نیست.
- فقط تراکنش‌های تأییدشده در جمع قطعی درآمد و هزینه وارد شوند.
- `fallbackToDestructiveMigration` ممنوع است.
- متن پیامک و داده بانکی نباید در Logcat نسخه Release چاپ شود.

## محدوده فعلی

فاز ۳ هنوز شروع نشده است. در پایان فاز دوم نباید این موارد پیاده‌سازی شده باشند:

- NotificationListenerService
- Parser پیامک و اعلان بانکی
- گزارش‌ها و نمودارهای نهایی
- رابط کامل بودجه‌بندی
- قابلیت‌های مراحل بعدی

## اولین وظیفه بعد از دریافت سورس

1. ساختار فایل‌ها را فهرست کنید.
2. هرگونه Secret، `local.properties`، Keystore و فایل تولیدی را از Git خارج کنید.
3. Entity، DAO، Repository، Use Case، Hilt و Migration را با اسناد تطبیق دهید.
4. `assembleDebug` و Unit Testها را اجرا کنید.
5. تست‌های Instrumentation قابل اجرا را روی دستگاه/شبیه‌ساز اجرا کنید.
6. اختلاف میان گزارش قبلی و واقعیت کد را مستند کنید؛ چیزی را صرفاً به‌دلیل ذکرشدن در این سند موجود فرض نکنید.
7. بدون تأیید کاربر وارد فاز ۳ نشوید.

## روش همکاری کم‌مصرف

- هر دستور فقط یک قابلیت کوچک را پوشش دهد.
- بعد از هر تغییر کوچک کل پروژه دوباره ممیزی نشود.
- Build کامل و مجموعه تست جامع در پایان هر فاز اجرا شود.
- قبل از شروع مرحله بعد، یک Commit/Checkpoint سالم ایجاد شود.
- اگر کار به محدودیت مدل خورد، دستور از ابتدا تکرار نشود؛ ابتدا تغییرات موجود بررسی و فقط بخش باقی‌مانده ادامه یابد.
